## 唯一拟议的代码变更

1. 数值风险按 **BF16 相邻可表示值的间距**计算：取原 packed 行 top2 两个 BF16 logit，在各自量级计算向上、向下相邻值的最大间距 `u`，若 `top1 - top2 <= 2 * u` 则触发重核。这里 `29.875` 附近 `u=0.125`，阈值为 `0.25`，会覆盖本例的 `0.125`。这是一项事先锁定的 **2-ULP 启发式**，不是数值误差的数学上界；不得把通过有限样本写成对任意提示的正确性证明。记录原 margin、`u`、阈值、触发行及两次决策。
2. 每轮首次触发后，从该行起直到首拒或实际需要的 bonus，**所有后续已用决策行**均用与独立 Target AR 相同的 BF16、同一真实完整前缀、无 cache 的 Target 前向取得 Greedy `argmax`、合法 hidden 与 logits；这是为了不在同一轮把重核后的已接受决策与原 packed 数值历史混用。首拒后停止，不重算未使用的 proposal；EOS 或预算不需要 bonus 时不重算 bonus。第 `i` 个 proposal 的决策前缀严格为 `confirmed + proposals[:i]`；bonus 行为 `confirmed + proposals`。只用当时已经存在的 token，不读取将来纠正 token 或未来 Target 输出。最终决策以该前向的 `argmax` 为准，不能查预存 AR 答案或改变 Target Greedy 规则。
3. 对需要继续解码的重核决策，另用相同有效前缀的 `use_cache=True` 前向构造可提交的 KV，按确认长度裁剪；不能把原长 packed 查询的 KV 与 canonical 决策混接。无 cache 决策和 KV refill **各算一次额外 Target 前向**，记录真实调用数、同步 GPU 时长、峰值显存和每轮来源。若实现对后来未成为最终 commit 行的触发行也提前 refill，同样全额计费。原 packed verify、重核、refill、特征来源诊断分别计数，不能把诊断调用混入生产成本。
4. 保持锁定模型、BF16、数据、窗口、独立 AR oracle、EOS/截断规则、8 原始字节协议与 F/C/B 容量约束；源码与协议升版、旧失败和原始源码逐 SHA 留存。不得在已冻结的 source_v1 上原地改写。

## 复验顺序与停止规则

1. 隔离实现的 CPU 单元测试先覆盖 0、1、2 ULP 边界、负数与幂边界、首次拒绝、全部接受 bonus、EOS、无后续 bonus、KV 裁剪和额外前向计费；随后在真实 BF16 GPU 上重放本次第二条失败训练提示及此前第一个失败训练提示（各 128 token），逐 token/EOS/截断对独立 AR 核验。
2. 完整重跑冻结的六条训练提示 × 两臂 GPU P0，包括所有分支、特征因果来源、KV 与显存 gate。前述单条重放不能代替完整 P0。任一 gate 失败则暂停采集和训练，保留原始 JSON、日志、源码及哈希。
3. P0 通过后才对冻结 train 1000 / val 200 采集计划重新建独立版本目录；所有请求逐条完整 token/EOS/截断一致，失败行原样保存，不删样本、不改阈值、不跳过请求。先完成 train 采集正确性，再执行 val 数据采集和冻结后续训练/评估；不得用 val 接受率调整本数值门槛或窥视封存 test。
4. 重新测量该真实后端的触发率、额外 Target 前向、wall time、显存及成本阈值，旧 margin=0 微基准只作历史参照。若收益不足以覆盖真实增加成本，按冻结方案报告负结果，不宣称 packed 加速、WAN 收益或 64-bit 方法成功。
5. **停止无限加阈值**：若出现原 packed margin 大于本次 2-ULP 阈值而仍与独立 AR 分歧，保留该请求并定位；不得把阈值从 2 ULP 反复抬高直到样本通过。可以另做“所有已用决策行均完整前缀”的明确标记诊断并全额计费，用于判明数值边界；若需要这种逐行回退才正确，或成本门槛失效，则按 P0 `BLOCKED` /成本 `NO-GO` 交接，不进入 P1 质量训练。有限通过不能被说成普遍保证。

本次修订的唯一可接受目标是让 **已测轨迹**满足冻结的独立 AR 正确性，同时诚实计入新增 Target 成本。是否进入 P1 由重新运行的完整 gate 和预登记成本判定决定。
